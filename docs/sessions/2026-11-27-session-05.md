# Session 05 Log (2026-11-27) — Crackle root cause: 32-bit WebView on little cores

1. Reproduced over CDP (single-process debug, `window.__rs`): engine context 0.357× with the transport stopped; fresh context 1.0×.
2. Ruled out: Tone.Context wrapper around a fresh native context (1.0×); Tone's orphan default context (closing it: no change); analysers/ConstantSources/oscillators in isolation; stale chain rebuilds (3 extra full rebuilds: 0.31 → 0.28×).
3. Hooked `BaseAudioContext.create*` before load: 1,586 nodes on the engine context (≈1,250 per full build of the default project). Disconnecting every node → context catches up instantly; render load is the cost.
4. Thread scan: the WebView renderer's `Realtime AudioW` thread at 96% CPU, only ever on cores 0-3. Whole renderer, and `webview_zygote`, have `Cpus_allowed_list: 0-3`; the app process and Chrome's foreground renderer have 0-7.
5. Cause: `com.android.webview` 113 has `primaryCpuAbi=armeabi-v7a`; `aarch32_el0` = 0-3, so the 32-bit renderer can only use the A520 little cores. Chrome 158 is arm64.
6. Fix: `settings global webview_multiprocess = -2147483648` (single-process WebView: the renderer runs in the 64-bit app process). `MainActivity.forceSingleProcessWebView()` applies it on launch when `WRITE_SECURE_SETTINGS` has been granted over adb (manifest + `device:dev` grant).
7. Verified on the standalone APK after deleting the setting: the app re-applied it on first launch, no sandboxed process, 0.999× while playing, 0 late steps, audio thread ~59% on core 7.
8. Pending: user listening test; re-test the worklet features with the guard off.

## Idle CPU optimisation (audio thread, single-process WebView, default project)
Measured per-thread CPU over adb (`/proc/<pid>/task/*/stat`; the render thread is `Realtime AudioW` when a worklet is loaded, else `ThreadPoolSingl`/`AudioOutputDevi`; names change across reloads).
1. `Tone.Freeverb` = 8 AudioWorklet combs per instance, ~5 points of a big core each in real time (~10.5% offline). Replaced by `src/audio/native-freeverb.js` (DelayNode feedback loops, same topology/tunings). Verified **bit-exact** vs Tone.Freeverb on an impulse (corr 1.000, energy 1.000; 128 frames less latency). Notes: Chrome adds one render quantum to a DelayNode closing a cycle (subtract 128 frames); use whole-sample delays (`floor(fround(t)*sr)+1`) like Tone's worklet, or linear interpolation smears the loop (-24% energy).
2. `Tone.Filter` wires 4 `Tone.Signal` ConstantSources into each biquad's params: 0.38 points/instance vs 0.08 for `Tone.BiquadFilter`. Swapped everywhere except mono303 (`rolloff: -24`).
3. Result: idle **52% → 36%**, playing ~40%, rate 1.000, 0 late steps. With no worklet loaded, Chrome renders on its normal audio thread again.
4. Measured and small: meters (all 30+ analysers ≈ 3 points), punch FX + limiter ≈ 2, returns ≈ 2, rebuilds/dispose do not leak.
5. Remaining cost is per-node graph traversal spread over ~1,000 nodes (DRUM-8 ≈ 1.4, VERB ≈ 1.3, DELAY ≈ 1.0 per instance). `ctx.resume()` after suspend takes 8-15 ms until audio flows (relevant for an idle auto-suspend).
